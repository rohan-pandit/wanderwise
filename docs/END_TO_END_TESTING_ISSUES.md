# End-to-End Testing Issues

A standing, persistent log of issues found during manual end-to-end testing of the running app (as opposed to automated eval/unit-test failures, which live in their own suites). Separate from `IMPLEMENTATION_PLAN.md` §5, which tracks deferred architectural/design decisions and known boundaries — this file tracks concrete bugs found by clicking through the real app.

Each entry gets a status and, once resolved, a note on how/where it was fixed. Nothing is deleted — closed entries stay for the history of what broke and when.

## How to use this file

- When manual testing turns up a bug, add an entry below before moving on.
- Work through entries one at a time: decide fix-now vs. defer for each, per the project's standing practice.
- A deferred entry that turns out to be a permanent scope boundary rather than a bug should be moved to `IMPLEMENTATION_PLAN.md` §5 instead of staying here.

The cold-start into the flight step was the one place with two independent trigger paths instead of one.

- [x] **#6 — A live trip (`0464978b-6e75-46ba-bf0f-765a6467aac6`, Paris from JFK) got permanently stuck, and `proposeFlightStep` looped continuously (~1 call/second) for over 4 minutes, well past the flight step's own confirmation.** Reported live 2026-09-18 by the user ("current trip session is stuck") while testing the just-shipped activities-in-chat change. Caught and fixed in real time, mid-incident — diagnosed against the trip's own `trip_events` (263+ `flight_step_proposed` rows, identical candidate each time, ~0.6-1s apart, continuing well after `flight_step_confirmed` and `hotel_step_proposed` had already fired) and the dev server's own request log (confirmed the *client* was the source — repeated `POST .../trips/0464978b.../` → `proposeFlightCandidates` calls, not a server-side loop).

  **Real bug, a latent one exposed rather than newly introduced**: `ItineraryPanel`'s flight/hotel auto-propose effect (`app/app/_components/itinerary-panel.tsx`) guards against re-firing using a content signature derived from `decisions` (`flightSigRef`/`hotelSigRef`) — but `proposeFlightStep`/`proposeHotelStep` write as two separate steps (retire the old "proposed" rows, *then* insert the new ones), which Realtime delivers as two separate messages. In the gap between them, `decisions` can transiently show *no* proposed rows for that field, which the signature-based guard couldn't tell apart from a genuinely new external change (e.g. a chat-driven revision) — it looked identical, so the effect refired, which retired+reinserted again, reproducing the exact same gap, forever.   **Fix**: added an explicit in-flight guard (`flightProposingRef`/`hotelProposingRef`) that's checked *in addition to* the signature, so the component's own pending write is never mistaken for an external change while it's still settling. Also changed what the signature ref gets set *to*: instead of a `decisions` snapshot taken before the call (which is exactly the value that goes stale mid-flight), it's now derived from the call's own result once it resolves — deterministic regardless of Realtime delivery timing, so a later *genuine* external change (a real revision) is still correctly detected. Applied to both the flight and hotel branches (the same retire-then-insert shape exists in both); activities' own auto-hydrate path was already safe — it's gated by a plain once-per-transition boolean, not a content signature, so it was never vulnerable to this specific mechanism.

  **Live remediation**: the fix alone didn't stop the already-running loop in the user's already-mounted tab (stale refs, old JS) — had them reload, confirmed via the dev server's request log and the trip's `trip_events` (no new `flight_step_proposed` rows in the 30+ seconds after reload, `hotel_step_proposed` firing cleanly once) that it actually stopped, not just paused.

Reproducible on any reload of any already-confirmed trip, unrelated to today's other issues. Fixed by hydrating both summaries from a direct client-side `flights`/`hotels` read (both world-readable seed inventory, confirmed via `supabase/migrations/0001_initial_schema.sql`'s RLS policies) in the same effect that already fetches `trip_decisions` on mount.

  Verified: `npx tsc --noEmit`/`npm run lint`/`npm test` (450/450, unchanged) all pass; dev server compile log clean. Both fixes confirmed live against the actual incident trip — the loop stopping (DB event timeline + request log, above) and the reload-hydration fix compiled in immediately after (not yet independently re-verified with a fresh reload showing a real airline name; the user's next reload of a confirmed trip will confirm).
