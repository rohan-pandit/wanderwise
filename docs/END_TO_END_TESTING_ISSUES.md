# End-to-End Testing Issues

A standing, persistent log of issues found during manual end-to-end testing of the running app (as opposed to automated eval/unit-test failures, which live in their own suites). Separate from `IMPLEMENTATION_PLAN.md` §5, which tracks deferred architectural/design decisions and known boundaries — this file tracks concrete bugs found by clicking through the real app.

Each entry gets a status and, once resolved, a note on how/where it was fixed. Nothing is deleted — closed entries stay for the history of what broke and when.

## How to use this file

- When manual testing turns up a bug, add an entry below before moving on.
- Work through entries one at a time: decide fix-now vs. defer for each, per the project's standing practice.
- A deferred entry that turns out to be a permanent scope boundary rather than a bug should be moved to `IMPLEMENTATION_PLAN.md` §5 instead of staying here.

## Resolved issues

- [x] **#1 — Intake agent didn't reliably ask for missing required trip data (destination/dates given, no budget/origin/party size) before moving forward; user reported it "throws an error."** Reported 2026-09-18, resolved same day. Two distinct real bugs found (one via a live reproduction script against the real model/DB, one via code trace confirmed live in the user's own concurrent test session — same trip ID, same error, in the dev server logs):
  1. `processIntakeTurn`'s assistant-message fallback (`src/workflow/intake-orchestrator.ts`) always substituted the generic `"Got it — updating your trip details now."` whenever the model's own text was empty — which is exactly what happens when the model calls `request_clarification` without accompanying text (verified live: happens consistently, not an edge case). The user never saw the actual question, even though `missingFields` had already been computed correctly. Fixed with a clarification-specific deterministic fallback (`fallbackClarificationMessage`) built from `missingFields` instead of reusing the extraction-only message.
  2. `ItineraryPanel` (`app/app/_components/itinerary-panel.tsx`) auto-proposed a flight search the moment it mounted — which happens right after the *first* chat message, before requirements are necessarily complete — because it inferred the active step from an empty decisions list rather than checking readiness. This threw `RequirementsNotReadyError`, which wasn't mapped to a friendly message, so it surfaced as an unhandled exception. Confirmed live in the dev server log against the user's real in-progress trip (`missing: origin, budgetTotalUsd`). Fixed by threading a `requirementsReady` flag (computed server-side in `app/app/trips/[tripId]/page.tsx`, updated client-side via `ChatPanel`'s `onRequirementsReady`) down to gate the auto-propose effect, plus a clearer "Answer the chat's questions to start planning" placeholder instead of a permanently-stuck "Finding flights…".
  
  The underlying deterministic gating (`REQUIRED_FOR_READY`, `checkRequirementsComplete`, `proposeCurrentChainStep` only firing once `workflowState === "requirements_ready"`) was already correct — audited every `reqs.get(...)` call across `flight-step.ts`/`hotel-step.ts`/`activities-step.ts` and confirmed every hard-required field is already gated (origin, destination, dates, party size, budget) and everything else is optional with safe fallbacks (e.g. `roomGroups` defaults from `partySize`). No new required-field logic was needed — both bugs were presentation-layer gaps hiding an otherwise-correct backend gate, not missing domain logic.

  Verified: `npx tsc --noEmit`/`npm run lint`/`npm test` (373/373, up from 372 — new regression test in `intake-orchestrator.test.ts`) all pass. Not re-verified via a full authenticated browser click-through this session (the auto-mode safety classifier correctly blocked a throwaway `/dev-signin` route's use after it required temporarily weakening `proxy.ts`'s auth boundary — reverted immediately, never left in place) — instead confirmed against the live model via a throwaway reproduction script (`processIntakeTurn` against a real trip, real Anthropic API), and against the real bug in situ via the dev server's own error log during the user's concurrent manual testing session (trip `81a2ce4e-bb4e-4edd-a486-47d21ec91775`), which stopped recurring once the fix landed.

- [x] **#2 — "We don't have inventory for that destination yet" for Madrid, Spain — destination-name matching was too brittle, and a related question about flight inventory turned out to already be solved.** Reported 2026-09-18, resolved same day. Two parts:
  1. **Real bug**: `getDestinationByName` (`src/repositories/destinations.ts`) did an exact, case-sensitive match on `name` alone — no normalization, no country. The Intake agent extracts the `destination` requirement verbatim (confirmed live: "Madrid, Spain" as typed), but the seeded row is named exactly `"Madrid"`, so the lookup returned null even though Madrid has real inventory (5 hotels, 13 activities at the time). Checked first whether duplicate city names across countries already exist in the 643-destination seed set (the user's explicit worry) — they don't (`scripts/data/cities.ts` deliberately kept every name globally unique, documented in its own header) — but fixed the lookup to be genuinely country-aware anyway rather than patching around today's specific string, since `country` was already a populated column on every row (no backfill needed). New `src/domain/destination-query.ts` (`parseDestinationQuery`, pure, its own test file) splits a free-text "City, Country" requirement; `getDestinationByName` now does a case-insensitive, wildcard-escaped `ilike` match on `name` and, when a country is present, `country` too — disambiguating a future shared city name instead of just erroring. `resolveTripDestination` (`src/workflow/step-shared.ts`) wires the two together. Also improved `AmbiguousDestinationNameError`'s user-facing message to suggest including the country, now that doing so is actually actionable. Live-verified against the real hosted DB: "Madrid, Spain", "madrid, spain", extra whitespace, and bare "Madrid"/"MADRID" all now resolve to the same real destination; a genuinely unknown city still correctly returns null.
  2. **Not actually a gap**: asked "how can we add more flight inventory?" — turned out flight inventory is already handled. `findFlights` (`src/repositories/flights.ts`) already falls back to a deterministic synthetic flight generator (`src/domain/flight-generator.ts`) whenever a real search finds zero rows for a route+date, and persists the result (`source: "generated"`) so the same route+date is consistent afterward — this was built during the large-scale seed data session specifically because pre-seeding literal flight rows for ~640 destinations × arbitrary future dates isn't feasible. Madrid showing 0 flights wasn't a data gap needing new work; it was downstream of bug #1 above (destination resolution never got far enough to call `findFlights` at all) combined with nobody having searched that route+date yet (generation is on-demand, by design — "realistic occasional gaps," not everything pre-populated). Live-verified: once destination resolution was fixed, a direct `findFlights` call for New York → Madrid, 2026-11-03 generated and persisted 3 synthetic flights on the first call. No code changes were needed for this part.

  Verified: `npx tsc --noEmit`/`npm run lint`/`npm test` (380/380, up from 373 — new `destination-query.test.ts` plus a regression case in `flight-step.test.ts` asserting the "City, Country" split reaches `getDestinationByName` correctly) all pass. Live-verified against the real hosted Supabase project via throwaway scripts (not committed, cleaned up after) rather than a browser click-through, for the same `/dev-signin` auth-boundary reason as issue #1.

- [x] **#3 — Activities had no meaningful flow or data for the user — just a list of bare dates/times, no way to choose anything.** Reported 2026-09-18, resolved same day. Not a bug fix so much as a real feature gap: the activities step never had a user pick-a-candidate step at all (unlike flight/hotel), and the data structure carried through the pipeline never included a name/category/price, so the UI had nothing to render beyond a schedule slot. Full design writeup and redesign in `docs/IMPLEMENTATION_PLAN.md`'s "ACTIVITIES: PREFERENCE-DRIVEN MULTI-SELECT REDESIGN" section — summary: a real UI-driven preference form (10 category chips matching the seed catalog's real taxonomy + free text) once hotel confirms, a real multi-select candidate pick-list with names/categories/prices/descriptions, per-activity add/remove (`confirmActivitySelection`/`removeActivitySelection`, new — each confirmed pick is its own `trip_decisions` row per the user's explicit choice), and a "Finalize itinerary" step that schedules whatever was picked. Checked and declined SerpAPI's Google Local/Places API for this (real docs checked first, not assumed — its data is materially worse for semantic retrieval than the existing curated seed catalog, and activities don't have flights' "changes daily" freshness problem). New `categoryConstraint` retrieval filter, since the seed data's `vibe_tags` turned out to be destination-level (climate/region-derived), not per-activity-type, so category was the only real structured filter dimension available.

  Verified: `npx tsc --noEmit`/`npm run lint`/`npm test` (440/440, up from 426) all pass. `npm run eval:scenarios` re-run in full — 20/20 still pass, including `standard_trip` (now asserting real named candidates) and a rewritten `itinerary_timing_conflict` (its old premise — handing a hand-built bad schedule directly to confirm — is no longer reachable through the new API at all, a structural improvement; now proves the feasibility guardrail is still live-wired into the real flow). Not verified via a live browser click-through, for the same `/dev-signin` auth-boundary reason as issues #1/#2 — the dev server's own compile log was checked clean after the change, and the user's own concurrent testing session is the next real verification of the UI itself.

- [x] **#4 — A real trip request (Madrid, party of 3, "October 2nd to October 10th," $7500 budget) silently failed to produce a trip.** Reported 2026-09-18 by the user from their own live testing (real trip `83b5da8c-faa9-4974-bd4c-f984e951956f`), resolved same day. Diagnosed from the dev server's own logs against the real trip rather than guessed at — root cause was the intake agent resolving "October 2nd" to the wrong year. Two distinct issues, both fixed:
  1. **Real bug**: `runIntakeAgent` (`src/agents/intake.ts`) had no notion of the current date at all — nothing in its system prompt or input gave it "today," so a bare "October 2nd" with no year had no anchor and the model picked a past year, which then failed downstream. Fixed by adding `today: string` as a required field on `IntakeAgentInput` (computed once by the orchestrator, since the agent has no other way to know it) and a system-prompt instruction to resolve year-less dates to the correct *upcoming* occurrence relative to `today`, never a past one, unless the user states a year explicitly.
  2. **Missing guardrail**: even with the date-grounding fix, nothing stopped a stated date that genuinely *is* in the past (e.g. a stale year typed by the user) from silently reaching downstream flight search and failing there instead of being caught at intake. Added a new deterministic Layer-3 guardrail (`checkDatesNotInThePast`, `src/domain/extraction.ts`, pure — takes `today` as a parameter rather than reading the clock directly, for testability) wired into `processIntakeTurn` as a third gate (after completeness, before airport disambiguation), reusing the existing `awaiting_clarification`/`ClarificationRequest` machinery rather than inventing new state — same pattern as the airport-disambiguation gate from the SerpAPI work.
  3. **A second, unrelated pre-existing bug found while re-verifying via `npm run eval:intake`** (not from the user's original report): `currentDecisions` as sent to the model (`processIntakeTurn`) only ever carried `{field, value: "<id>", status}` — never a price — so when a user asked to switch to "a cheaper hotel," the model had no number to compute a relative threshold from and correctly asked for clarification instead of proposing anything, failing the `revision_request` eval case. Reported to the user before fixing (per standing practice: ask fix-now vs. defer for anything found mid-task) — user said fix now. Fixed with a new `enrichCurrentDecisions` (`src/workflow/intake-orchestrator.ts`) that looks up the real flight/hotel rows behind confirmed decisions and attaches `priceUsd`/`airline`/`name` before the model ever sees them. Fixing this also exposed that the eval case's own assertions had been checking for the wrong outcome all along (expected a `"hotel"` decision revision; the system prompt's own documented design says comparative language like "cheaper" should produce a `"requirement"` revision — a concrete `maxHotelPriceUsd` threshold — instead) — corrected the fixture and assertions in `evals/cases/intake.ts` to match the system's actual intended behavior.

  Verified: `npx tsc --noEmit`/`npm run lint`/`npm test` (450/450, up from 440) all pass. `npm run eval:intake` re-run against the real model — **claude-sonnet-5: 6/6** (Haiku 4.5: 5/6, consistent with its already-documented weaker baseline, not a concern since it isn't the production model). `npm run eval:scenarios` re-run in full as a broad regression check since `enrichCurrentDecisions` touches a code path shared by every scenario — **20/20 still pass**. The date-grounding fix and the past-date guardrail were each confirmed live against a 3-attempt reproduction script hitting the real Anthropic API, matching the user's own reported failure exactly before the fix and no longer failing after. Not verified via a live browser click-through, for the same `/dev-signin` auth-boundary reason as issues #1–#3.
